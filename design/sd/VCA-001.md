# SOLDEF_VoiceCallAI_ST-101.md

## SOLDEF-ST-101 — Grounded Multilingual Telephony AI Assistant & Streaming Control System (FastAPI Modular Monolith)

### Project Details

* **Project ID:** PROJ-VOICE-001
* **Project Name:** Grounded Multilingual Telephony AI Assistant ("Theodore")

### Story Details

* **Story ID:** ST-101
* **Story Name:** Real-time Conversational Telephony Core, Live Grounded Search/Maps, Public Transit Guidance, Tool-Based Media/Reminders & Low-Latency Audio Streaming Pipeline
* **Story Description:**
Design and implement the production architecture for "Theodore", an interactive telephony voice assistant built on a Python FastAPI modular monolith following strict architectural separation (`agents`, `tools`, `prompts`, `client`, `service`, `repository`, `schema`, `database`, `settings`, `constants`, `utils`, `exception`, `routes`, `models`, `dependencies`). The system manages bi-directional 8kHz linear PCM telephony WebSockets (via Vobiz.ai) and web studio simulator audio channels. It supports bilingual (Tamil and English) dialogue handling, live internet grounding via Gemini models (`ChatGoogle` with `@langchain/google`), tool-encapsulated capabilities for YouTube audio streaming (`yt-dlp` + `ffmpeg`), outbound voice reminders, RSS news aggregations, and instant voice barge-in stream termination with a seamless conversation reset workflow.

###  Section 1: Functional Requirements 

####  1.1 Overview 

This story implements the core conversational telephony pipeline conforming to the **FastAPI Agent Development Standard**. The directory structure divides concerns cleanly: API endpoints reside in `src/routes/`, reusable business logic in `src/service/`, LangGraph orchestrators in `src/agents/`, discrete executable actions in `src/tools/`, versioned voice prompts in `src/prompts/`, external SDK wrappers in `src/client/`, and ORM-first database entities in `src/schema/` and `src/repository/`. The voice assistant executes real-time 8kHz PCM streaming over WebSockets, evaluates incoming utterances with Voice Activity Detection (VAD), routes user requests through LangGraph agents, executes tool-encapsulated capabilities (Web Search, Maps, Transit Guardrails, Reminders, YouTube Audio Piping), and handles instant voice interruptions (barge-ins) to stop active media playback and pivot to new conversational instructions without dropping the call.

#####  1.2.1 REQ-001: Bi-directional Telephony & Web Audio WebSocket Orchestrator 

##### Description:

Implement a bi-directional WebSocket handler (`src/routes/call_stream_routes.py`) that accepts Vobiz.ai telephony streams or web studio inputs, unpacks 8kHz mono PCM or μ-law frames, processes speech through Voice Activity Detection (VAD), and dispatches transcripts to the LangGraph session service.

##### Process Flow:

1. Client establishes WebSocket connection at `/api/v1/telephony/stream/{session_id}`.
2. `src/service/call_session_service.py` initializes the state checkpointer for the session ID.
3. Incoming audio frames are analyzed by VAD; silence > 600ms determines speech turn boundaries.
4. Transcribed text passes into the LangGraph orchestrator (`src/agents/call_orchestrator_graph.py`).
5. Generated response text is synthesized via Inworld TTS client (`src/client/inworld_tts_client.py`) and streamed back as 8kHz PCM chunks.

##### Acceptance Criteria:

1. WebSocket server successfully handles concurrent active voice streams without packet loss.
2. VAD isolates conversation turns with sub-600ms latency.
3. Every session interaction logs structured audit telemetry with `session_id` and `correlation_id`.

#####  1.2.10 REQ-010: Audio Barge-In Interrupt, Stream Cutoff & Conversation Reset Handling 

##### Description:

Implement instant user override during active media streaming (e.g., when YouTube music or a news bulletin is playing) by detecting speech via VAD, immediately terminating streaming subprocesses, clearing audio buffers, resetting session state, and processing the new user intent as a fresh turn (`src/service/call_session_service.py`).

##### Execution Workflow for User Action Interruption:

1. **Active Streaming State**: The system is piping audio frames (e.g., streaming a song from YouTube or reading a long news bulletin). Session `playback_state` is set to `"streaming"`.
2. **VAD Detection During Playback**: The inbound WebSocket channel continues monitoring client audio frames. If VAD detects user speech energy exceeding the interruption threshold for > 200ms:
* **Step 1 (Immediate Network Halt)**: The server dispatches a buffer-clear command across the Vobiz WebSocket link to flush client-side audio playback buffers.
* **Step 2 (Subprocess Termination)**: Active `yt-dlp` and `ffmpeg` transcoding processes or active Inworld TTS streaming generators are sent immediate termination signals (`SIGTERM`/`SIGKILL`), cutting off data flow instantly.
* **Step 3 (State Reset & Pivot)**: Session state variables update instantly (`active_media_stream = null`, `playback_state = "idle"`), flushing pending output tokens. The graph orchestrator resets its listening pointer to accept fresh input.


3. **Seamless Pivot to New Conversation**: The incoming user utterance (e.g., *"Stop music, tell me tomorrow's weather"* or *"Change song to classical"*) is captured cleanly as a brand-new user intent. The assistant acknowledges the change naturally (*"Okay, stopping that. Here is the weather..."*) without requiring a call disconnect or reconnect.

##### Acceptance Criteria:

1. Audio playback and streaming subprocesses halt within 300ms of detecting user voice energy during active streaming.
2. State flags successfully reset from `"streaming"` to `"idle"`, clearing all dangling data handles.
3. The system immediately comprehends and executes the new user command without call dropouts or connection resets.

###  Section 2: Non Functional Requirements 

### 2.1 Infrastructure and Deployment

####  2.1.1 Overview 

The application deploys as a containerized FastAPI modular monolith on AWS EC2 or Amazon EKS, connected to an AWS RDS PostgreSQL instance following the standard layout in `FASTAPI_AGENT_DEVELOPMENT_STANDARD.md`. WebSocket stream handling utilizes `uvicorn` with `uvloop` to support high-concurrency non-blocking I/O. Secrets (Gemini, Inworld, Vobiz API keys) are managed securely via environment injection from AWS Secrets Manager into Pydantic BaseSettings (`src/settings/settings.py`).

####  2.1.2 Requirement Details 

* **NFR-001: Asynchronous WebSocket Stream Concurrency**
* *Acceptance Criteria*: Container configuration supports at least 100 concurrent active telephone calls with sub-millisecond frame dispatch and low memory footprint (< 40MB per session).


* **NFR-002: Subprocess Lifecycle & Zombie Process Prevention**
* *Acceptance Criteria*: 100% of spawned `ffmpeg` and `yt-dlp` media subprocesses are cleanly destroyed using process-group signals within 1 second of call termination or barge-in interruption.

### 2.2 Architecture and System Design

####  2.2.1 Security and Compliance 

* **Data Protection**: Raw audio streams are processed entirely in-memory; audio files are never written to disk or persistently recorded. PII is redacted from text logs.
* **Secrets Management**: Credentials are loaded dynamically via validated Pydantic `Settings` (`src/settings/settings.py`) and are strictly excluded from source code and logs.



####  2.2.2 System Performance 

* **Latency SLAs**: VAD detection (< 300ms), Search Grounding response (< 1200ms), TTS Stream Start (< 800ms), YouTube Audio Pipeline Start (< 1500ms), Total Turnaround Target (< 1800ms).

####  2.2.3 Availability and Reliability 

* **Graceful Degradation**: External search tool failures gracefully fall back to model core weights with an explanatory spoken notice.

####  2.2.4 Cost Efficiency 

* **Token Budgeting**: Optimized by invoking `gemini-3.8-flash` and restricting search tool routing exclusively to real-time intent nodes (shopping, transit, news).

####  2.2.5 Traceability and Observability 

* **Structured JSON Logging**: Centralized logger (`src/utils/logger.py`) attaches `correlation_id`, `session_id`, `node_name`, and execution latencies to every log entry.
